# M3-C11: Validation, Guardrails & Explainability

## Core Guardrails (Assertions)
1. **Reachability/Compatibility**: Never rank an unreachable or incompatible station highly. These MUST be pushed to the bottom of the recommendation list, and the reason MUST explicitly call out why (e.g., "Warning: You may not have enough battery...").
2. **Confidence Bounds**: Never emit a forecast or window confidence outside the interval `[0, 1]`.
3. **Data Provenance**: Never present a mock or low-confidence value without its explicit tag. The `quality` tag inside `GridSnapshot` ensures clients know if data is `live`, `cached`, `stale`, or `mock`.
4. **Explainability**: Recommendations must include a human-readable `reason` string referencing the actual deciding factor (e.g. travel distance penalty, connector incompatibility).

## Implementation
- `app/guardrails.py` intercepts responses right before they are serialized and returned by the FastAPI routers.
- It iterates through the outputs and raises a 500 error (`GuardrailViolation`) if any rule is broken. This ensures a bad response fails loudly during testing.
- A dedicated `test_guardrails.py` suite explicitly constructs "bad" responses and verifies that the guardrails catch them.

## Deterministic Mocking
- The core data ingestion engine uses a seeded random number generator (`MOCK_SEED=42`) when generating grid snapshots. 
- This guarantees reproducible demos without needing live external API keys, ensuring that every pitch sees the exact same consistent Indian diurnal grid curves.
