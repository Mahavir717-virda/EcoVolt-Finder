## 1. Objectives & Scope

Implement authentication and role-based access control (RBAC) per `/contracts/openapi.node.yaml`:
1. **Password Hashing:** Use `bcryptjs` with salt factor 12 for secure, constant-time password verification.
2. **Token Strategy:**
   - **Access Token:** Short-lived JWT (15 minutes), signed with `JWT_SECRET`. Contains payload `{ sub: userId, email: string, role: Role }`.
   - **Refresh Token:** Long-lived JWT (7 days), signed with `JWT_REFRESH_SECRET`. Used to obtain new access tokens at `POST /auth/refresh`.
3. **Endpoints to Build:**
   - `POST /auth/signup` — Register user with validation, emit access & refresh tokens and user profile.
   - `POST /auth/login` — Authenticate email/password, emit access & refresh tokens.
   - `POST /auth/refresh` — Exchange valid refresh token for a new access token.
   - `GET /me` — Fetch authenticated user profile (`id, name, email, role`).
   - `PATCH /me` — Update user profile (e.g. `name`).
4. **Middleware:**
   - `requireAuth`: Extracts `Bearer <token>`, verifies access token, attaches `req.user` (`{ id, email, role }`). Emits 401 if missing/invalid/expired.
   - `requireRole(...roles: Role[])`: Validates `req.user.role` is in allowed list, emits 403 `FORBIDDEN` otherwise.
   - `requireStationOwnership`: Ensures a `manager` can only modify stations owned by their operator. Emits 403 `FORBIDDEN` if not owner.
   - `authRateLimiter`: Stricter rate limit on `/auth/*` (e.g., 20 requests / 15 minutes) to prevent brute-force attacks.
5. **Validation:** Strict `zod` schema validation on all request payloads.

## 2. Key Edge Cases Addressed

- **Edge Case #22 (Manager edits another manager's station):**
  The `requireStationOwnership` middleware checks if `station.operator.userId === req.user.id` or if user is `admin`. If not, it rejects with HTTP 403 Forbidden.
- **Edge Case #24 (Invalid credentials & input validation):**
  - Login failure returns uniform message `"Invalid email or password"` without leaking whether the email or password was the invalid component.
  - Malformed inputs (e.g., email not formatted, password < 8 chars) are rejected with HTTP 422 / 400 Validation Error.
- **Unique Constraint on Signup:**
  Registering with an already existing email returns HTTP 409 Conflict with code `EMAIL_ALREADY_EXISTS`.

## 4. Acceptance Criteria & Verification

1. `POST /auth/signup` creates a user in PostgreSQL and returns `{ accessToken, refreshToken, user: { id, name, role } }`.
2. Duplicate signup returns `409 Conflict`.
3. `POST /auth/login` with correct credentials returns tokens.
4. `POST /auth/login` with wrong password returns `401 Unauthorized` with generic message.
5. `GET /me` without token returns `401 Unauthorized`.
6. `GET /me` with valid access token returns `200 OK` and user info.
7. `PATCH /me` updates user name and persists changes.
8. `POST /auth/refresh` with valid refresh token returns `{ accessToken }`.
9. `requireRole([Role.manager])` allows managers/admins and rejects drivers with `403 Forbidden`.
10. `requireStationOwnership` blocks managers attempting to mutate foreign stations with `403 Forbidden`.
11. Full TypeScript compilation (`tsc`) succeeds with 0 errors.
